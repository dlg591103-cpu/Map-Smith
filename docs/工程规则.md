# 工程规则

本文件是本项目工程规则的唯一正文。`README.md`、`AGENTS.md`、`docs/Spec/` 下的 SPEC 等文件只引用本文件，不复制规则内容；规则的新增与修改只在本文件进行。

适用范围：本项目 Git 仓库（项目根目录）内的开发、自检、独立验收、Git 操作，以及与之配套的文档更新。

## 1. 分支与基线

- `main` 保持稳定，始终可交付。
- 每项开发开始前，先确认基线。基线指 `main` 上一个固定的提交。
- 从确认的基线创建独立任务分支，开发与自检都在该分支上完成。
- 不在 `main` 上直接开发，不使用未经确认的提交作为基线。

## 2. SPEC 先行

- 开发前先确认本次任务对应的 SPEC（见 `docs/Spec/`）。
- SPEC 写清目标、修改范围、预期行为、必要依赖与验收条件，并引用相关产品事实，不复制整套产品设定。
- 开发与测试使用同一份 SPEC：开发方按 SPEC 检查实现，验收方按 SPEC 检查验收结果。

## 3. 交付与固定提交

- 开发完成后交付明确的提交及自检结果。
- 独立验收针对这份固定提交进行，验收期间不更换提交。
- 验收期间如需修改，则产生新提交，重新记录自检与验收结果。

## 4. 自检与独立验收分别记录

- 研发自检与独立验收分别记录，各自独立成文，不做合并叙述。
- 发现问题后先修复，再检查受影响的部分；修复范围涉及其他功能时，补充相应的回归检查。
- 验收通过后，按用户授权合并回 `main`。

## 5. 职责划分

- 开发、自检、独立验收、Git 合并四项职责需分别明确，不默认由同一执行者同时承担开发与独立验收。
- 具体由哪些人或 AI 会话执行，由用户确定后补充到本文档；未确定前，在任务记录中如实注明每项工作的实际执行者。

## 6. 合并与上线

- 合并与上线分别处理，合并完成不等于已上线。
- 上线必须经用户明确确认后方可执行。
- 只记录实际完成的操作和检查结果；未执行或未验证的范围必须明确说明，不得推定通过。

## 7. 文档同步

- 修改涉及产品事实、接口或数据规则时，同步更新对应的责任文档（产品事实见 `docs/facts/`）。
- 同一项内容只在一个位置维护，其他文件以链接引用，不做副本。

## 8. 复用与改动边界

- 修改前先检查已存在的代码和组件是否可以复用。
- 不顺便修改无关功能；确有必要改动的，单独说明原因与范围。

## 9. 证据与清理

- 保留必要的交付证据和失败证据，包括提交、自检记录、验收记录与失败日志。
- 完成后清理本次不再需要的临时文件、测试服务和进程。
- 任务验证并合并后，再清理对应的任务分支及工作树。

## 10. 仓库与远端

- 项目根目录是唯一的 Git 仓库，稳定分支为 `main`；`src/` 是应用源码子目录。
- `docs/` 与根目录管理文件同属该仓库，随同一份提交与远端同步，不再单独保存或备份。
- 远端为私有仓库 `https://github.com/dlg591103-cpu/webgis-twin-lab`，`main` 跟踪 `origin/main`。
- 提交身份为 `hpzi <265828292+dlg591103-cpu@users.noreply.github.com>`，配置在仓库级，不依赖全局配置。
- 推送、拉取等远端同步操作须经用户授权后执行。网络受限时按用户认可的方式配置代理（本机 `127.0.0.1:7890`，配置项为全局 `http.proxy` / `https.proxy`）；代理停用后相应撤销。
- 不自行创建远端仓库，不声称未实际完成的同步。
